ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ИТОГОВАЯ ВЕРСИЯ)
на разработку приложения «Switch Port Manager» (SPM)
Версия: 1.0 (прототип)
Дата: 13.08.2026
Стек технологий: C#, .NET 9.0, ASP.NET Core, Entity Framework Core, SQLite, SSH.NET, LDAP (Active Directory)

1. Цели и задачи
1.1 Бизнес-цели
Снизить нагрузку на отдел сетевой инфраструктуры за счёт делегирования рутинных операций по настройке портов сотрудникам технической поддержки.

Сократить время перенастройки портов до 2 минут на операцию.

Обеспечить возможность настройки портов сотрудниками техподдержки без предоставления им прямого доступа к оборудованию и учётным данным.

1.2 Задачи проекта
Разработать веб-интерфейс и мобильное приложение (iOS/Android) для управления портами.

Интегрировать аутентификацию и авторизацию через Active Directory (LDAP).

Реализовать SSH-подключение к свитчам с использованием логина/пароля, хранящихся в зашифрованном виде.

Внедрить ролевую модель: Администратор и Оператор (в прототипе реализуются только функции администратора).

Обеспечить хранение информации о свитчах, правах доступа и последнем известном состоянии портов в SQLite (временное решение, в будущем – PostgreSQL).

2. Область применения
Приложение предназначено для использования внутри корпоративной сети.
Поддерживаются свитчи с доступом по SSH (CLI), поддерживающие команды настройки VLAN и режимов Access/Trunk (в прототипе – только Cisco-like).

3. Функциональные требования
3.1 Роли пользователей
Роль	Описание
Администратор	Полный доступ: управление свитчами, правами доступа, просмотр и настройка любых портов, управление учётными данными устройств.
Оператор	Доступ только к разрешённым администратором свитчам и портам. Не видит логины/пароли, не может добавлять/удалять оборудование. (Операторская часть реализуется после прототипа.)
3.2 Варианты использования (Use Cases) для прототипа
В первом прототипе реализуются только сценарии для администратора. Операторские Use Cases откладываются на следующий этап.

ID	Название	Описание
UC-01	Просмотр списка свитчей	Таблица со всеми свитчами, фильтрация, сортировка, пагинация. Данные – из локальной БД.
UC-02	Просмотр информации о свитче и его портах	В прототипе данные о портах (режим, VLAN, статус up/down) читаются напрямую с оборудования по SSH при каждом запросе (без кеширования). Результат парсится и сохраняется в БД для возможности отображения при ошибках.
UC-03	Настройка порта как Access	SSH-команда на свитч, после успеха – обновление БД.
UC-04	Настройка порта как Trunk	Аналогично UC-03.
UC-05	Добавление свитча	Ввод IP, модели, логина, пароля, описания; проверка доступности по SSH.
UC-06	Удаление свитча	Удаление свитча и всех связанных данных (порты, права).
UC-07	Редактирование свитча	Изменение любых параметров (кроме прав доступа).
UC-08	Управление доступом к свитчу для оператора	Назначение прав: просмотр в списке, детальный просмотр, настройка портов.
UC-09	Управление правами на порт	Разрешение/запрет оператору изменять VLAN для Access и/или Trunk на конкретном порту.
Важно: В прототипе кеширование состояния портов отсутствует – каждый вызов UC-02 инициирует SSH-сессию. Это допустимо для малой нагрузки и позволит отработать механизм взаимодействия с оборудованием. В продуктивной версии будет добавлен кеш с TTL.

3.3 Входные и выходные данные по Use Cases
UC-01 – Просмотр списка свитчей
Вход: фильтр (IP, модель, описание), сортировка (поле, направление), пагинация (страница, размер).

Выход: массив объектов (ID, IP, модель, описание, статус доступности), общее количество, применённые параметры.

UC-02 – Детальный просмотр свитча
Вход: ID свитча.

Выход: информация о свитче (из БД) + массив портов с полями: номер, режим (Access/Trunk), VLAN (или список разрешённых VLAN), состояние (up/down), скорость/дуплекс (если доступно).
В прототипе данные всегда свежие (с оборудования), время выполнения логируется. При ошибке SSH – возвращается сообщение об ошибке; если в БД есть сохранённые данные, они могут быть показаны с пометкой «устаревшие».

UC-03, UC-04 – Настройка порта (Access/Trunk)
Вход: ID свитча, номер порта, VLAN ID (для Access) или список VLAN (для Trunk).

Выход: статус операции, новое состояние порта (подтверждение от оборудования). После успеха – запись в БД обновляется.

UC-05 – Добавление свитча
Вход: IP-адрес, модель, логин, пароль, описание (опционально).

Выход: ID созданного свитча, результат проверки SSH-доступа.

UC-06 – Удаление свитча
Вход: ID свитча.

Выход: статус удаления.

UC-07 – Редактирование свитча
Вход: ID свитча, изменяемые поля.

Выход: обновлённый объект свитча.

UC-08 – Управление доступом к свитчу
Вход: ID свитча, ID оператора, флаги прав (can_view_list, can_view_detail, can_configure_ports).

Выход: подтверждение.

UC-09 – Управление правами на порт
Вход: ID свитча, номер порта, ID оператора, флаги (can_change_access_vlan, can_change_trunk_vlans).

Выход: подтверждение.

4. Нефункциональные требования
4.1 Технические ограничения
Бэкенд: C# .NET 9.0 (ASP.NET Core Web API).

ORM: Entity Framework Core 9.0 (Code First).

БД: SQLite (временное хранилище, в будущем – PostgreSQL).

SSH: библиотека SSH.NET (Renci.SshNet) – асинхронная.

Аутентификация: LDAP (Active Directory) через System.DirectoryServices.Protocols или аналоги; выдача JWT-токенов.

Фронтенд (Web): SPA (React/Vue) – взаимодействие через REST API.

Мобильное приложение: .NET MAUI (кросс-платформенное) – для базового просмотра.

Документация API: Swagger/OpenAPI.

4.2 Производительность
Время отклика для операций чтения (UC-01) – не более 1 секунды.

Время выполнения SSH-команды – не более 10 секунд (с таймаутом).

Поддержка одновременной работы не менее 50 пользователей (в прототипе – 10).

4.3 Безопасность
Пароли свитчей хранятся в зашифрованном виде (ASP.NET Core Data Protection с мастер-ключом из переменных окружения).

Все API-методы защищены атрибутом [Authorize].

HTTPS обязателен для всех клиентов.

Логирование каждого действия (кто, когда, что, результат) с сохранением в таблицу AuditLog.

4.4 Надёжность
Обработка ошибок SSH – повторные попытки (до 2 раз), запись в лог.

В случае ошибки чтения портов – возвращается информативное сообщение; данные из БД могут быть показаны как устаревшие.

5. Архитектура приложения
5.1 Общая структура (N-слойная / Clean Architecture)
Domain – сущности (Switch, Port, User, Permission, PortPermission, AuditLog).

Infrastructure – репозитории (EF Core), SSH-сервис, LDAP-сервис, шифрование, провайдер состояния портов.

Application – сервисы Use Cases (SwitchService, PortService, PermissionService).

Web API – контроллеры, middleware для аутентификации, обработки ошибок, логирования.

5.2 Работа с портами (прототип)
Интерфейс IPortStateProvider – в прототипе реализован как DirectSshPortStateProvider, который при каждом вызове GetPortStatesAsync() выполняет SSH-запрос к свитчу.

После получения данных они сохраняются в БД (обновляются записи портов) для возможности отображения при следующем запросе, если возникнет ошибка.

Изменение порта (UC-03/04) выполняется через SSH, затем БД обновляется.

Планируемое улучшение: в следующих версиях будет добавлен CachedPortStateProvider с TTL и фоновым обновлением.

6. Требования к интерфейсам
6.1 Веб-интерфейс (администратор)
Страница «Свитчи» – таблица с фильтрацией, сортировкой, пагинацией, кнопка «Добавить».

Страница детального просмотра – вкладки: общая информация, порты (таблица с текущим состоянием, считываемым с оборудования), права доступа.

Кнопка «Обновить» для ручного перечитывания состояния портов (повторный SSH-запрос).

Модальные окна для добавления/редактирования свитча, настройки порта (выбор VLAN, режима).

Подтверждение опасных действий (удаление).

6.2 Мобильное приложение (прототип – только просмотр)
Список свитчей, доступных администратору.

Детальный просмотр с таблицей портов.

Кнопка обновления.

6.3 REST API
Все операции доступны через REST с JWT-аутентификацией (возможны изменения).

Документация Swagger.

7. Безопасность и аудит
Пароли свитчей никогда не передаются на клиент.

Все запросы проходят проверку прав (на уровне сервисов или через политики авторизации).

Логирование всех действий пользователей с указанием IP-адреса.

Использование HTTPS для всех соединений.

9. Критерии приёмки
Веб-интерфейс и мобильное приложение успешно проходят аутентификацию через AD.

Администратор может добавить свитч, просмотреть его порты (с актуальными данными с оборудования), настроить порт как Access/Trunk – изменения применяются на оборудовании.

При ошибке SSH пользователь получает понятное сообщение; при наличии сохранённых данных они отображаются с пометкой об устаревании.

Ни один интерфейс не показывает пароли свитчей в открытом виде.

Все действия залогированы с указанием пользователя.

Время выполнения операции настройки порта не превышает 10 секунд.

10. Ограничения и допущения (прототип)
Поддерживается только один вендор (HP на OS: Comware5, Comware7) – парсинг вывода команд жёстко завязан на формат show running-config interface, show interfaces status.

Кеширование состояния портов отсутствует – каждый запрос UC-02 обращается к оборудованию.

Фоновая синхронизация не реализуется.

Операторские Use Cases не реализуются в прототипе.
